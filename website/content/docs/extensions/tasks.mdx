---
title: Tasks
description: Durable tool execution, polling, input requests, cancellation, and subscriptions.
---

Tasks turn eligible `tools/call` requests into durable work. Enabling the extension requires an `McpTaskProvider`; the adapter deliberately does not ship an in-memory production default.

```ts
app.use(mcp({
  extensions: {
    tasks: {
      version: 'current',
      provider,
      defaultTtl: 86_400_000,
      pollInterval: 1_000
    }
  }
}))
```

Set `taskExecution` on an explicit tool or route:

- `synchronous` always returns the normal tool result.
- `optional` creates a task when the request declares Tasks support and otherwise runs synchronously. This is the default for task-capable tools.
- `required` rejects clients that do not declare the required request capability.

The provider owns cryptographically unguessable IDs, durable creation, read-after-write visibility, retrieval, partial input updates, cooperative cancellation, expiry, execution scheduling, and subscriptions. A created task must be visible through `tasks/get` before it is returned. In a distributed deployment, task records and subscription fan-out must be shared across instances.

`TaskProvider.create` receives a structured-clone-safe `TaskDurableCreateRequest` and a normalized context containing only the selected Tasks version, request metadata, and verifier-derived principal key. Persist those values as the durable job descriptor. Its separate `TaskExecutionScheduler` argument is an ephemeral, same-process invocation handle that preserves the normal Elysia route lifecycle; never serialize, retain, or send that handle to a worker. External workers should consume the durable descriptor and execute through their deployment's MCP worker boundary.

The provider records a resolved tool result as `completed` even when that result has `isError: true`; `failed` is reserved for a JSON-RPC execution failure. Cancellation is cooperative and may remain pending until the executor observes the durable cancellation intent.

Explicit handlers receive `context.task`. Route handlers use `getMcpTaskContext(request)`; the adapter associates the controller with the internal `Request` through a private `WeakMap`, never a model-controlled header.

Final `2026-07-28` tasks can request elicitation, sampling, or roots input. Request keys are unique for the full task lifetime. `subscriptions/listen` acknowledges before streaming complete `notifications/tasks` snapshots and cleans up on disconnect.

Tasks are unavailable on legacy `2025-11-25`. There is intentionally no task-listing operation. When Auth is enabled, every task is bound to the verifier-derived principal key, including polling, updates, cancellation, and subscriptions.

Applications should define retention and expiry limits, cap subscription fan-out, persist cancellation intent, encrypt sensitive task data, and avoid storing raw credentials in task records.
